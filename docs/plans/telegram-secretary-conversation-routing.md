# Telegram: контекст диалога секретаря и доставка API-переписки

Статус: план согласованного поведения, реализация не начата.
Дата: 2026-10-21.

## Цель

Пользователь видит в Telegram начало и продолжение общения с секретарём,
независимо от того, кто задал вопрос — пользователь в Telegram или агент через
API. Для каждого сообщения понятно, к какому диалогу оно относится и куда
уйдёт ответ. Фоновые сообщения не переключают активный диалог автоматически.

Этот документ разрешает только планирование. Реализация, запуск сервисов,
миграция рабочей БД и развёртывание требуют отдельного поручения. Соблюдать
`AGENTS.md` и правила пользователя, включая отдельный `GO` для правок кода.

## Подтверждённое текущее состояние

- Диалоги хранятся в `conversations` и имеют UUID `id`. Короткого номера у
  диалога нет. Короткий номер задачи, например №41, — другая сущность.
- `conversation_runtimes` хранит привязку диалога к профилю секретаря и внутренней
  сессии Runner (`runner_session_id`), максимум одну запись на диалог.
- Активный Telegram-контекст хранится отдельно в `telegram/state.py`.
  Входящий обычный текст маршрутизируется по этому состоянию. Сейчас
  `on_user_message` не выбирает диалог по сообщению, на которое сделан Reply.
- Telegram-клиент записывает сообщения с `source=telegram`;
  `POST /conversations/{id}/messages` по умолчанию использует `source=api`.
  `/ask` и `/conversations/ask` также создают сообщения через репозиторий.
  Telegram сам обращается к backend через HTTP, поэтому факт HTTP-запроса
  не различает пользовательский Telegram-ввод и внешний API-ввод.
- Обычный Telegram-ответ доставляет `telegram/worker.py`, где уже используется
  `InputRichMessage`. Он не является общей доставкой всех API-диалогов.
- `task_subscriptions.py` отдельно доставляет ответы секретаря на события
  завершения задач. Отправка текста использует `parse_mode=None`, без кнопок
  выбора диалога. Это объясняет отсутствие форматирования в данном пути.
- Сегодня в журнале есть создание подписки в 08:26:43, завершение задачи в
  08:27:53 и завершение хода секретаря в 08:28:12 (UTC−3). Эта последовательность
  соответствует описанному сообщению; отдельной записи, однозначно связывающей
  Telegram message ID и этот ответ, в исследованном журнале нет.
- Причина недоставки вчерашнего конкретного ответа не установлена. Не считать
  её доказанной потерей сообщения или тем же самым сценарием без проверки.

Рабочая копия и установленная версия `task_subscriptions.py` на момент
исследования совпадали. Исходные сообщения и журналы не изменялись.

## Согласованное поведение

### 1. Полный UUID в сообщениях

Использовать полный существующий `conversation_id`. Не добавлять короткие
номера, сокращённые UUID или отдельный пользовательский идентификатор сессии.

В конце каждого сообщения бота, относящегося к диалогу, выводить хештег:

```text
#34acbd180d064f6d8588a039c0f1b6bc
```

Пример показывает формат, а не конкретный ID для реализации. Один и тот же
UUID присутствует на копии API-вопроса, ответе, связанных уведомлениях,
ошибках и последующих сообщениях этого диалога. Если ответ разбит на несколько
сообщений или отправлен вложением, контекст должен быть виден у каждой части
и в подписи вложения. Глобальным командам без диалога не назначать вымышленный
UUID. Исходные пользовательские сообщения Telegram изменять не требуется.

UUID обозначает диалог, а не задачу, отдельный ход модели или внутреннюю
сессию Runner. Возобновление Runner не меняет UUID диалога. Явно созданный
новый диалог получает свой UUID.

Хештег — средство чтения, копирования и диагностики. Маршрутизация и проверка
доступа не должны зависеть от извлечения UUID из видимого текста.

### 2. API-вопрос и ответ всегда видны в Telegram

Для общения владельца с секретарём через API доставлять в его Telegram-чат:

1. Копию исходного вопроса с пометкой «Вопрос секретарю через API» и UUID.
2. Ответ секретаря с тем же UUID. Ошибка исполнения также должна быть видна.

Если достоверно известен вызывающий агент, показывать его имя. Не выдавать
произвольный текст из metadata за подтверждённую идентичность вызывающего.
Копировать именно вопрос, а не служебный промпт, учётные данные или весь
технический контекст запуска. Пользовательские вложения сохраняют связь с
сообщением; детали существующей доставки файлов не должны теряться.

Охватить как `/ask` и `/conversations/ask`, так и обычный путь
`messages` → `turns`. Повтор HTTP-запроса, который вернул уже существующее
сообщение или ход, не должен создавать новую копию вопроса или ответа.

Вопрос должен быть доставлен раньше соответствующего ответа. Это порядок
Telegram-доставки; успешное выполнение модели не обязано ждать доступности
Telegram. Если у диалога пока не определён чат владельца, сохранить доставку
как ожидающую и явно диагностировать отсутствие адресата. Не выбирать чужой
чат или текущую активную задачу как замену адресату.

Telegram-вопрос уже находится в чате: повторно отправлять его копию не нужно.
Ответы на события подписок также доставляются, но системное событие нельзя
подписывать как новый пользовательский API-вопрос. Формат сообщения должен
различать API-вопрос, ответ секретаря и результат фоновой задачи.

### 3. Reply направляется в исходный диалог

Хранить устойчивую связь:

```text
Telegram chat ID + Telegram message ID
    → conversation_id + backend message/turn reference + связанная задача, если есть
```

Связывать с диалогом исходные пользовательские сообщения, копии API-вопросов,
ответы бота, их части и вложения. Связь сохраняется после перезапуска.

При входящем Telegram Reply сначала определить диалог исходного сообщения,
проверить принадлежность владельцу и только затем обрабатывать текст, медиа
или ответ на уточнение задачи. Активный режим пользователя не должен
перехватить такой ответ. Особенно проверить существующий путь
`waiting_for_input`: Reply в другой диалог не должен возобновлять задачу №41.

Reply отправляет конкретное сообщение в исходный диалог, но сам по себе
не переключает активный контекст для следующих сообщений без Reply.

Если связь для сообщения бота потеряна, диалог удалён либо недоступен,
показать понятное объяснение и предложить выбрать диалог. Не отправлять
такой ответ молча в активную задачу. Для Reply на посторонние сообщения
явно определить и проверить поведение при реализации; не угадывать диалог
по процитированному тексту или хештегу.

### 4. Явная кнопка переключения контекста

У сообщений диалога предоставить кнопку «Продолжить этот диалог».
Для сообщения из другого диалога явно показать отличие от текущего контекста,
например: «Другой диалог · сейчас активна задача №41».

Нажатие кнопки:

1. Проверяет существование и доступность диалога для пользователя.
2. Устанавливает его активным, сохраняя его реальную связь с задачей, если она есть.
3. Подтверждает выбранный контекст и показывает полный UUID.

Если диалог уже активен, повторное нажатие безопасно и не создаёт новый диалог.
Если сообщение пришло в фоне, активный контекст остаётся прежним. Обычный
текст без Reply идёт в явно выбранный активный диалог.

Плашка «сейчас активна…» отражает состояние на момент отправки сообщения;
старое сообщение не является вечным индикатором текущего состояния. Подтверждение
переключения должно однозначно показывать новый контекст.

### 5. Единая доставка, форматирование и диагностика

Объединить правила оформления и доставки секретарских сообщений из Telegram,
API и подписок. Сохранить форматирование Markdown через общий механизм
рендеринга, кнопки, UUID и передачу файлов. При невозможности применить
форматирование сохранить читаемый текст и контекст; ошибка разметки не должна
терять само сообщение.

Доставка должна иметь устойчивое состояние в БД. Перезапуск между вычислением
ответа и отправкой не теряет ответ и не запускает модель заново. Уже
подтверждённые отправки и части не пересылаются при штатном восстановлении.
Не добавлять произвольных бизнес-ограничений или лимитов числа сообщений.
Технические ограничения Telegram учитывать вместе с подписью UUID и разметкой.

Не обещать недостижимую гарантию exactly-once: при сетевом тайм-ауте Telegram
может принять сообщение до потери подтверждения. Этот случай отдельно
диагностировать; выбрать и документировать стратегию восстановления.

В диагностике связывать источник сообщения, `conversation_id`, backend message
ID, `turn_id`, Telegram chat/message ID и результат доставки. Для входящего
Reply фиксировать выбранный диалог и основание выбора. Для переключения —
предыдущий и новый UUID. Не писать секреты или весь текст переписки в журнал
по умолчанию.

## План реализации

Приступать только после отдельного разрешения на код. Использовать актуальную
карту архитектуры; границы ниже — подтверждённые исходные точки, а не разрешение
читать весь проект. Во время реализации держать не более одного этапа в работе.

### Этап 1. Устойчивые связи и события доставки

Результат: backend-сообщение, доставка и Telegram message ID связаны независимо
от текущего состояния Telegram-пользователя.

Вероятные файлы:

- `src/agent_manager/storage/models.py`
- `src/agent_manager/storage/repository.py`
- новый специализированный модуль хранения доставки при необходимости
- `migrations/versions/` — новая Alembic-миграция
- `src/agent_manager/telegram/state.py` — совместимость с существующим состоянием

Перед изменениями уточнить, как сообщения и доставка будут транзакционно
сохраняться в основной БД. Не строить надёжность на несогласованных записях
в двух SQLite-базах. Сохранить существующие диалоги, UUID и привязки Runner.

Сначала добавить проверки миграции, долговечности связей, повторной регистрации
одного события и восстановления после перезапуска. Для SQLite использовать
временную файловую БД, настройки соединений и WAL по правилам проекта.

Не выполнять миграцию рабочей БД в рамках локальной реализации. План отката
миграции должен учитывать, что удаление таблиц доставки уничтожит её историю;
без отдельного разрешения рабочие данные не удалять.

### Этап 2. Общая отправка в Telegram

Зависит от этапа 1.

Результат: единый отправитель формирует человекочитаемый контекст, полный UUID,
кнопку, форматированный текст и вложения, а затем сохраняет Telegram-связи.

Вероятные файлы:

- новый общий модуль Telegram-доставки/оформления
- `src/agent_manager/telegram/worker.py`
- `src/agent_manager/telegram/keyboards.py`
- `src/agent_manager/task_subscriptions.py`
- `src/agent_manager/runner.py` — подключение фоновой доставки

Проверить обычный ответ, ответ подписки, ошибку, длинный ответ, вложение,
сбой форматирования и перезапуск между отправками частей. Сохранить смысл
существующих тестов подписок: повтор доставки не запускает секретаря заново.

### Этап 3. Зеркалирование API-переписки

Зависит от этапов 1–2.

Результат: новый API-вопрос попадает в очередь Telegram-доставки; его ответ
проходит тот же механизм. В Telegram соблюдается порядок «вопрос → ответ».

Вероятные файлы:

- `src/agent_manager/api/app.py`
- `src/agent_manager/api/schemas.py` — только если нужны дополнительные данные
- `src/agent_manager/storage/repository.py`
- `src/agent_manager/secretary.py`
- `src/agent_manager/dispatcher.py`
- `src/agent_manager/task_subscriptions.py`

Выбирать точку создания событий по сохранению сообщений, а не только по
одному API-маршруту: это исключит расхождение `/ask` и `messages` → `turns`.
Не создавать второй механизм отправки того же ответа. Корректно отличать
Telegram-ввод, API-ввод и `task_event`.

Проверить оба API-пути, идемпотентный повтор, несколько вопросов в одном
диалоге, быстрый ответ, ошибку модели и временно недоступный Telegram.

### Этап 4. Reply и переключение диалога

Зависит от этапов 1–2; сквозная проверка включает этап 3.

Результат: Reply всегда выбирает исходный диалог, кнопка явно меняет активный,
обычный текст продолжает выбранный контекст.

Вероятные файлы:

- `src/agent_manager/telegram/handlers.py`
- `src/agent_manager/telegram/state.py`
- `src/agent_manager/telegram/client.py`
- `src/agent_manager/telegram/keyboards.py`
- API чтения связей/контекста при необходимости

Определять Reply-контекст до ветвления по режиму и до обработки уточнения задачи.
Сохранить маршрутизацию текста, голоса, фото и документов. Обработать устаревшие
кнопки, отсутствующие связи и недоступные диалоги без скрытого перехода в другой.

### Этап 5. Сквозная проверка и документация

Результат: воспроизводится исходная ситуация с двумя диалогами без потери
контекста, а история API-разговора полностью видна в Telegram.

Вероятные проверки и файлы:

- `tests/test_telegram_handlers.py`
- `tests/test_telegram_worker.py`
- `tests/test_telegram_bot.py`
- `tests/test_task_subscriptions.py`
- `tests/test_api.py`, `tests/test_dispatcher.py`, `tests/test_migrations.py`
- новые тесты общего модуля доставки и хранения связей
- `docs/handbook/` — инструкция о контексте, UUID, Reply и доставке

Сначала воспроизвести ошибку тестом, затем изменить поведение и проверить
затронутые границы. Изменения старых ожиданий объяснить; проверки не ослаблять.
Проверить наличие и точные имена файлов перед запуском выбранных тестов.

Финальные команды из корня `agent-manager`:

```bash
PYTHONPATH=src .venv/bin/python -m pytest

git diff --check
```

Зафиксировать фактические коды выхода и пропуски. Живую проверку через Telegram
проводить только по отдельному согласованию: автоматические тесты не должны
отправлять сообщения пользователю. Для реализации не требуются Desktop
Computer Use, внешние браузеры или запуск постоянных сервисов.

## Критерии приёмки

- [ ] API-вопрос из диалога A виден в Telegram раньше ответа, оба содержат
  полный UUID A; обычный Telegram-вопрос не дублируется.
- [ ] `/ask`, `/conversations/ask` и `messages` → `turns` имеют одинаковое
  поведение доставки, включая ошибку исполнения и идемпотентные повторы.
- [ ] При активной задаче B входящее сообщение из A явно показывает другой
  контекст и не меняет активный диалог.
- [ ] Reply на вопрос, ответ, часть длинного ответа или вложение из A уходит
  в A, даже когда активна B, в том числе после перезапуска.
- [ ] Такой Reply не становится ответом на уточнение задачи B и не возобновляет её.
- [ ] После Reply в A обычный текст без Reply всё ещё идёт в B, пока пользователь
  явно не нажал кнопку перехода.
- [ ] Кнопка перехода в A подтверждает полный UUID; последующий обычный текст
  уходит в A. Повторное нажатие не создаёт новый диалог.
- [ ] Потерянная связь, удалённый диалог и отсутствие доступа не вызывают
  незаметной отправки в другой контекст.
- [ ] Короткие номера/сокращения UUID не добавлены. В каждом контекстном
  сообщении бота и подписи вложения присутствует полный UUID диалога.
- [ ] Ответы подписок используют те же форматирование, кнопку и UUID, что
  обычные ответы. Системное событие не выдаётся за API-вопрос пользователя.
- [ ] Ошибка Markdown не теряет текст, контекст и возможность продолжить диалог.
- [ ] Перезапуск и ошибка доставки не теряют ожидающие вопросы/ответы и
  не запускают секретаря заново; подтверждённые отправки штатно не дублируются.
- [ ] Неопределённый результат сетевой отправки выделен в диагностике, а
  фактическая стратегия восстановления описана без обещания exactly-once.
- [ ] По UUID и идентификаторам сообщения/хода/Telegram можно восстановить
  фактический путь доставки и маршрутизации ответа без полного текста в логах.
- [ ] Проверки зелёные; рабочие сервисы и БД не менялись без отдельного поручения.

## Что уточнить при реализации

1. Точное место хранения Telegram-связей и событий доставки, обеспечивающее
   согласованность с сохранением backend-сообщения.
2. Полный охват других секретарских сообщений и уведомлений: какие из них уже
   имеют диалог, а какие относятся только к задаче и не должны получать
   вымышленный UUID. Самостоятельно не создавать для них новые диалоги.
3. Как определяется Telegram-адресат для существующих API-диалогов без chat ID.
   Для текущего владельца можно использовать существующую настроенную связь;
   при нескольких владельцах не расширять адресацию на посторонние чаты.
4. Поведение Reply на сообщения, для которых связи ещё не существовали до
   обновления, и на посторонние сообщения чата. Не восстанавливать маршрутизацию
   догадками по тексту.
