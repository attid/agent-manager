# Агентная система для проектной разработки — спецификация 0.3

**Статус:** рабочая спецификация намерений, не техническое задание на реализацию.  
**Дата:** 16 октября 2026.  
**Происхождение:** 12 раундов обсуждения повседневных сценариев пользователя и уточнение первого этапа после проверки Pi Runner и nTasker.  
**Редакция 0.3 (17 октября 2026):** уточнены реестр агентов вне разработки, управление профилями через API, навыки по ролям, доступ к OpenViking для поиска и структура знаний проектов/компонентов. Согласован корень рабочей установки `~/.agent-manager/` и мастер-хранилище `knowledge/`; права записи анализатора в OV остаются открытым вопросом. Имя файла сохранено для существующих ссылок.  
**Принцип:** отделять подтверждённые пожелания от гипотез, которые нужно проверить на реальных задачах.

## 1. Замысел

Небольшая управляемая система, где человек ставит и уточняет задачи, оркестратор ведёт очереди и статусы, а специализированные агенты выполняют конкретную работу в ограниченных окружениях. Постоянными являются конфигурации ролей, знания о проектах, история и состояние задач. Запуск LLM — временная операция. Один агент не обязан соответствовать одному постоянно живущему процессу или одной длинной сессии.

**Не является целью:** сохранить Codex и OMP любой ценой; построить всё на Orca; создавать автономного руководителя, который сам решает, что выпускать в production; бесконтрольно увеличивать объём контекста и число агентов.

## 2. Базовые сущности

| Сущность | Смысл |
|---|---|
| Проект / рабочая область | Изолированный набор доступных файлов, определяющий область работы. Может быть частью большого продукта и даже находиться в одном репозитории с другой областью. |
| Агент проекта | Постоянная **логическая роль** с инструкциями, разрешениями, проектной памятью, настройками; не обязана быть живым процессом. |
| Задача | Главная долговечная единица: описание, состояние, вопросы, зависимости, результаты и ссылки на сессии. |
| Сессия исполнения | Временный запуск определённого harness и модели для конкретного этапа задачи. Может быть продолжена, прервана, заменена новой. |
| Оркестратор | В первую очередь обычная программа: очереди, запуск, статусы, блокировки, связи задач, журнал. |
| Секретарь / консультант | LLM-помощник для беседы, постановки и уточнения задач, объяснения статуса системы. Точная граница с исследователем пока не определена. |
| Исследователь («архитектор») | Возможный подготовительный исполнитель: изучает проект, находит факты, варианты реализации, необходимые файлы; **не** проводит приёмку/ревью. Не обязательно участвует в каждой задаче. |
| Ревью | Независимая проверка выполненных изменений; вначале может остаться skill/инструментом Antigravity/Gemini, а не отдельной постоянной ролью. |
| Анализатор сессий | Роль первого этапа: разбирает законченные и прерванные исполнения, извлекает проверяемые знания и предложения по улучшению. |

## 3. Подтверждённые рабочие правила

### 3.1. Приём и запуск

- Входящие заявки пока поступают через человека (телефон, мессенджер, почта и т. п.). Автосбор заявок не нужен в первой версии.
- Реестр задач в собственной БД хранит входящие, запланированные, выполняемые, ожидающие и законченные задачи. На первом этапе работа с ним идёт через Telegram и API; визуальная доска не обязательна.
- Человек выбирает, что принять в работу. После перевода задачи в рабочую очередь она может запускаться автоматически, если есть свободная рабочая область и нет препятствий.
- Не каждая формулировка сразу становится заданием на код: может потребоваться исследование вариантов или уточнение требования.
- Секретарь и исследователь могут **переписывать описание** задачи по результатам обсуждения; разработчик главным образом добавляет результаты, вопросы и артефакты, не подменяя цель задачи.

### 3.2. Параллельность и очередь

- **MVP: не больше одной исполняемой задачи на рабочую область (проект).** Следующие задачи в очереди.
- Независимые рабочие области (например, MTL Laboratory и MTL Decision) могут выполняться параллельно, даже если относятся к одному продукту; границы изоляции должны быть определены явно.
- DevOps-исполнители также обслуживают последовательные очереди своих объектов/серверов.
- Глобальный лимит одновременно работающих процессов нужен, чтобы не запускать все сто заявок разом. Конкретное число задаётся конфигурацией и нагрузочными измерениями (ожидаемый обычный масштаб — примерно 5–10 задач в день, но это не жёсткий предел).
- Срочное внеочередное выполнение или параллельная работа внутри одной области — возможная будущая функция, не MVP.

### 3.3. Ожидание, остановка, восстановление

- При существенной неоднозначности исполнитель прекращает домысливать и задаёт вопрос через карточку задачи.
- Короткое ожидание ответа от другого исполнителя может сохранять задачу «в ожидании»; если ответ нужен от человека и может прийти через дни, выполнение сворачивается и рабочая область освобождается.
- Восстановление **задачи** важнее точного восстановления шага исполнения. После сбоя допустимо продолжить старую сессию, создать новую с кратким handoff или восстановиться по Git diff и описанию задачи.
- После перезапуска оркестратор сопоставляет карточки с действующими запусками и возобновляет нужное, не дублируя уже выполненные внешние действия без проверки.
- К задаче привязываются все относящиеся сессии, диагностические материалы, ревью и итоговые ссылки.

### 3.4. Разработка, ревью, завершение и публикация

- Для типового изменения желаемая схема: **разработка → независимое ревью → тот же разработчик исправляет замечания с сохранением контекста → проверка/ревью при необходимости → commit/push → задача разработки завершена**.
- Исполнитель может сам запускать локальные тесты и инструменты проверки в рамках разрешений. Существующий CI запускается после push; оркестратору незачем дублировать специфические тестовые команды.
- Замечания ревью, не относящиеся к цели изменения, не должны бесконечно расширять текущую работу: важные посторонние проблемы превращаются в **отдельные предлагаемые задачи**.
- В качестве начального ограничения обсуждается **до трёх циклов ревью**. Если после третьего остаются серьёзные проблемы или цикл повторяется, требуется разбор человеком; это гипотеза, а не окончательный норматив.
- Финализация commit/push может выполняться разработчиком, skill или отдельным исполнителем: вопрос пока открыт.
- **Публикация на production — отдельная задача**, которую человек ставит явно, иногда на конкретное время. Завершённая задача разработки сама по себе не разрешает деплой.
- После деплоя оператор фиксирует проверку запуска и минимальной работоспособности.

### 3.5. Наблюдение и коммуникация

- Первые интерфейсы — Telegram для человека и API для внешних агентов и инструментов. Оба дают доступ к одному секретарю и общему состоянию задач. Веб-интерфейс откладывается на второй этап, когда реальные сценарии прояснят поля и представления.
- Желательно видеть активную сессию и её действия. Интерактивное вмешательство в середине исполнения не является обязательным для MVP: можно остановить и перезапустить с уточнениями.
- Изменения состояний ведут журнал. Завершения и вопросы можно отправлять в Telegram. Степень подробности уведомлений решается после наблюдения за реальной частотой.
- Разработчик предположительно не запускает других проектных агентов напрямую: возвращает потребность в данных как состояние/вопрос задачи. Маршрутизация происходит через диспетчер и очередь. Это предпочтение, а не жёстко закрытое решение.

## 4. Изоляция и доступ

- Базовая единица ограничения — конкретная рабочая область. Агент проекта **не должен видеть соседние проекты**, даже для чтения «полезной библиотеки».
- Предпочтительный кандидат на локальную изоляцию Ubuntu — Bubblewrap, но механизм должен быть проверен с реальными инструментами/процессами.
- Разрешения должны действовать технически, независимо от текста prompt. Одна лишь рабочая папка (`cwd`) не ограничивает доступ к остальной файловой системе.
- У dev-агента нет необходимости в production-доступе. Общие технические сведения он получает через память/документацию, а не чтение чужих каталогов.
- У секретаря нет доступа к репозиториям проектов. Он получает только их описания, разрешённые summaries, карточки, события и материалы разговора через backend. Если нужны сведения из исходников, это отдельная исследовательская задача исполнителю с соответствующим доступом; предоставление памяти не должно обходить эту границу.
- Механизм секретов и прокси обсуждается отдельно и **не проектируется заново** в этой спецификации. Для DevOps используются уже принятые способы управления доступами.

## 5. Инструкции и память

### 5.1. Разделение источников

| Источник | Примерный смысл |
|---|---|
| `AGENTS.md` в репозитории | Общие правила разработки проекта, которые полезны любому разработчику этого репозитория. |
| Профиль агента в реестре системы (вне репозитория разработки) | Роль, инструкции, модель/harness, инструменты, разрешения, рабочие области, навыки и доступные разделы знаний. Управляется через backend API; файлы Runner могут быть производным представлением для запуска. |
| `PROJECT_OVERVIEW.md` / аналог | Обзор устройства конкретной рабочей области и важных интерфейсов. Формат пока не выбран. |
| `MEMORY.md` / аналог | Компактные, практически полезные знания, доступные при запуске или поиске. Не следует безлимитно наращивать обязательный prompt. |
| OpenViking / аналог | Поисковая память по проектам и по технологиям (FastAPI, Firebird, aiogram и т. п.), доступная нескольким релевантным агентам. Пока OpenViking **не выключаем**. |
| Архив задач и сессий | Полный фактологический след; не загружается целиком в новые задачи. |

### 5.2. Как улучшать память

- Стартуем с того, что уже есть в `AGENTS.md`, без попытки заранее составить идеальный стартовый контекст.
- На первом этапе **основной исполнитель решает задачу, отдельный анализатор разбирает законченные и прерванные исполнения**. Его вопрос: «Каких сведений не хватило, из-за чего было потрачено лишнее время, вызовы модели или инструменты?».
- Анализатор готовит проверяемые технические знания и сохраняет результаты в мастер-хранилище системы. Автоматическая запись в OpenViking не считается согласованной; возможные права анализатора ещё обсуждаются. Постоянные правила поведения отделяются от знаний и не переписываются автоматически без отдельного решения.
- Анализатор входит в первый этап. Его полезность и качество накопленных знаний проверяются на реальных задачах; преимущество перед короткой инструкцией о сохранении памяти пока не доказано. Выводы сохраняются со ссылками на исходные задачи, сессии и события; предположения отделяются от проверенных фактов.
- Сильные изменения проекта (например, переход SQLite → Firebird) должны запускать ревизию стартовых сведений. Частоту обновления определять активностью проекта, а не слепым календарём.
- Гипотеза «разогретый форк сессии» против «новая сессия + подготовленный обзор проекта» — **отдельный эксперимент**, не заранее принятое решение.

### 5.3. Агент как управляемые данные системы

- Агенты хранятся в системе, а не в каталоге разработки или папках отдельных экспериментов. Постоянны профиль и история; процесс LLM временный. Первые три роли — разработчик, секретарь и анализатор — должны стать записями одного реестра.
- Добавление и изменение агента выполняются через backend API без правки рабочего кода: идентификатор, назначение, инструкции, рабочая область/проект, harness/модель, инструменты, права, навыки и разделы памяти задаются данными. Новый агент на поддерживаемых инструментах не требует отдельной ветки в Python-коде. Добавление нового механизма исполнения или нового инструмента может потребовать расширения соответствующего адаптера.
- Секретарь должен иметь возможность создавать/редактировать профили через тот же API в пределах выданных полномочий. Он не редактирует конфигурационные файлы на диске и не меняет собственные разрешения произвольным текстом. Точный набор полей, доступных секретарю без дополнительного подтверждения, ещё согласуется.
- Профили, runtime-состояние, сессии и знания находятся в данных рабочей установки вне репозиториев разработки. JSON-конфиг для Runner и стартовый контекст могут формироваться из профиля перед запуском; они не являются отдельным ручным источником истины.
- Изменения профиля должны быть прослеживаемы. Исполнение связано с использованной версией инструкций/навыков/настроек; редактирование профиля не подменяет незаметно контекст уже работающего исполнения.

### 5.4. Навыки и стартовый контекст по ролям

| Роль | Требуемые знания и процедуры |
|---|---|
| Разработчик | `codespaces`: поиск по карте архитектуры, анализ границ и чтение релевантного кода. |
| Секретарь | Брейншторм и «прожарка» постановки: уточнение намерения, проверка допущений и подготовка задачи. Возможна адаптация или объединение этих процедур под роль секретаря. |
| Все роли | Небольшая инструкция поиска знаний в OpenViking: где искать сведения проекта и компонентов, как читать найденный источник. Без призывов сохранять всё подряд и без описания возможностей записи для обычного исполнителя. |
| Анализатор | Разбор исполнений, проверка выводов по источникам и подготовка материалов в мастер-хранилище. Право публикации в OV пока не утверждено. |

- Источник общих навыков — OpenViking. В каталоге подтверждены `viking://user/codex/skills/codespaces/`, `viking://user/codex/skills/brainstorming/` и `viking://user/codex/skills/grilling/`. Это ссылки на источники для будущего подключения; адаптация навыков в данном уточнении не выполнялась. Перед применением читаются полные инструкции и обязательные ссылки.
- Секретарю нельзя механически выдавать разработческие полномочия вместе с навыком: процедуры брейншторма/«прожарки» адаптируются к постановке задач по описаниям проектов, без исследования репозиториев.
- Отдельная идея для проверки: когда роли стабильно нужны два-три небольших навыка, их инструкции можно включать непосредственно в стартовый контекст, сохраняя связь с исходником и его версией. Пока это вариант реализации, а не принятое решение отключить механизм навыков или всегда загружать их целиком.
- Для навыков с исполняемыми ресурсами одного текста в prompt недостаточно: необходимые средства запуска должны быть доступны в изолированном окружении. Способ подключения `codespaces` и ресурсов OV в Bubblewrap необходимо проверить, а не считать уже готовым.

### 5.5. Память проектов и компонентов

- Нужны две раздельные области поиска: **память проекта** и **память компонента/технологии**. Наличие общих знаний не даёт доступа к исходникам соседнего проекта.
- Память проекта содержит его краткое описание, назначение, принятые решения, интерфейсы и проверенные особенности. Реестр проектов хранит описание, доступное секретарю, и связи с используемыми компонентами.
- Память компонента содержит знания, применимые в нескольких проектах: контракт, особенности использования, совместимость, проверенные решения и типовые проблемы. Компонентом может быть общая часть собственной системы или используемая технология, например FastAPI, Firebird или Pi Runner; точные категории и ключи уточняются.
- Проектные особенности остаются в памяти проекта; общие сведения — в памяти компонента. Между ними нужны ссылки, а не бесконтрольное копирование одной и той же заметки.
- Начальный маршрут поиска: краткое описание текущего проекта → релевантные проектные знания → знания связанных компонентов → исходные материалы по необходимости. Секретарю доступны только разрешённые описания и постановочные сведения, а не весь массив технических материалов проекта.
- Логическая структура: `projects/<project_id>/...` и `components/<component_id>/...`, с отдельными описаниями и связями «проект использует компонент». Это схема организации, а не утверждённые или уже созданные пути OV/файловой системы.
- OpenViking остаётся кандидатом на общее хранилище этих областей уже на первом этапе. Конкретные URI, маршруты поиска и связь с локальным мастер-хранилищем задаются конфигурацией и отдельной краткой инструкцией поиска; универсального поиска по всем чужим проектам по умолчанию нет.

### 5.6. Чтение OV и подготовка новых знаний

- Всем трём ролям нужен доступ к поиску и чтению разрешённых знаний OpenViking. Нельзя автоматически переносить в их контекст общие инструкции «записывать/remember всё полезное» и неотфильтрованный архив всех разговоров.
- Для разработчика и секретаря предусматривается доступ к OV только для чтения. Возможности записи не включаются в их инструменты и стартовую инструкцию. Это должно обеспечиваться выданным интерфейсом/правами, а не только просьбой в prompt; конкретный механизм ещё предстоит реализовать и проверить.
- Анализатор сохраняет отчёты и подготовленные знания в **мастер-хранилище системы** вне репозиториев. К материалу привязываются проект/компонент, исходная задача/сессия, ссылки на доказательства и степень проверенности. Это не разрешение автоматически переписывать правила поведения или публиковать каждый вывод как установленный факт.
- Открытое решение: оставить и анализатору OV только на чтение, публикуя проверенные материалы отдельной операцией backend, либо выдать ему специально согласованную запись. До такого решения автоматическая запись анализатора в OV не считается разрешённой.
- Согласовано: корень рабочей установки — `~/.agent-manager/`; мастер-хранилище знаний — `~/.agent-manager/knowledge/`, с разделами `projects/` и `components/`. Результаты исполнения и журналы хранятся отдельно в `sessions/`. OpenViking используется для поиска по согласованным разделам знаний; конкретный механизм публикации/индексации мастер-хранилища в OV ещё выбирается. Это целевая структура, а не утверждение, что перенос экспериментальных данных уже выполнен.

## 6. Изменяемость модели и harness

- **Логическая идентичность агента не должна зависеть от модели или harness.** Можно запускать Pi, DeepSeek Harness или другую совместимую реализацию, если сохраняются задачи, доступы, нужные инструкции и артефакты.
- Возможно использовать разные модели для разработки, ревью, анализа памяти и исследования.
- Идентичное возобновление *внутренней* сессии между разными harness не требуется. Для переносимости важнее задача, handoff, файлы и знания.
- Встроенные расширения/скиллы или отдельные исполнители выбираются по реальной пользе; создавать постоянную роль на каждое действие заранее не нужно.
- **Выбор модели/провайдера по умолчанию задаётся вне БД.** Обычный источник — глобальные настройки Pi (`defaultProvider`/`defaultModel`) или явно выбранный TOML-файл с таблицей `[default]`; в реестре профиля этот выбор хранить не обязательно. Секретарь наследует такой дефолт, а не «рабочую» модель текущего исполнителя.
- **Фиксированный per-agent override остаётся необязательным.** Если доверенная конфигурация роли уже содержит `provider`/`model`, она имеет приоритет и работает независимо от доступности файлов с дефолтами.
- **Закрепление prompt не закрепляет транспорт навсегда.** Разрешение дефолтов выполняется заново на каждое исполнение, поэтому правка файла дефолтов действует без изменения БД, без вызова модели и без перезапуска процесса.
- **Ручной/API-ремонт независим от LLM.** Повторный запуск и исправление конфигурации используют тот же резолвер и не требуют обращения к модели; смена файла дефолтов не переигрывает уже начатый (неопределённый) модельный вызов, а автоматическое согласование заблокированных сессий и политика failover в этот этап не входят.

## 7. Предлагаемые, но ещё не утверждённые статусы задачи

`Входящая` → `Уточнение` → `Готова к работе` → `В очереди` → `Выполняется` → `На ревью` → `Исправление` → `Завершена`.

Дополнительные состояния: `Ждёт человека`, `Ждёт другого исполнителя`, `Остановлена/ошибка`, `Отменена`. Это **черновая модель состояний**, а не обязательная структура колонок Trello: часть состояний удобнее хранить полями карточки.

Возможные поля карточки: ID, проект/рабочая область, формулировка, критерии результата, инициатор/приоритет, стадия, исполнитель, причины блокировки, вопросы/ответы, ссылки на сессии, ревью, diff/commit/CI, история переходов, связанные задачи.

## 8. Первые роли и типовые сквозные сценарии

**Первый этап включает секретаря, анализатора сессий и агента-разработчика самой системы.** Первые профили заводятся полуручно через реестр/API системы; добавление роли не требует изменения кода. Это логические роли, а не требование держать три процесса постоянно запущенными.

- Секретарь обсуждает намерения с человеком или внешним агентом через Telegram/API, уточняет и редактирует задачи, объясняет состояние. Переписка хранится отдельно от актуальной постановки задачи с сохранением связей между ними.
- Анализатор разбирает исполнения, выявляет недостающий контекст, повторные поиски и полезные технические знания. Изменения постоянных правил и инструкций предлагает отдельно, без автоматического применения.
- Агент-разработчик получает задачи по развитию системы через её ядро, работает в отдельной рабочей области, возвращает изменения, результаты проверок и вопросы. Разработка системы становится одним из первых реальных сценариев её использования.

Другие проектные профили и помощник по созданию агентов добавляются по накопленному опыту. Самостоятельный исследователь не обязателен для каждой задачи.

**Сценарий А — простое изменение:** человек принимает карточку → очередь проекта → исполнитель исправляет → ревью → замечания при необходимости → commit/push → карточка с результатом и ссылками завершена.

**Сценарий Б — ошибка на сервере:** карточка → при необходимости диагностическая задача DevOps → логи и факты прикладываются к задаче → проектный разработчик исправляет → ревью/commit → отдельно, после команды человека, создаётся задача деплоя → DevOps публикует и проверяет.

**Сценарий В — неполная постановка:** «Сделай красную кнопку» → секретарь задаёт общие уточнения → если для ответа нужны знания исходников, создаётся исследовательский шаг → согласованная постановка → очередь разработки.

**Сценарий Г — ожидание/авария:** исполнитель сохраняет вопрос, состояние и ссылку на сессию; долгий человеческий ответ освобождает очередь; после ответа или перезапуска машина возвращается к задаче без требования точно восстановить каждую модельную операцию.

**Сценарий Д — связные, но отдельные продукты:** InfoPark desktop / веб-отчёты API / устройства-«кубы» остаются самостоятельными рабочими областями. Документируется общий API/контракт и общие сведения о технологиях; доступ к чужим исходникам не открывается.

## 9. Первоначальные измерения и эксперименты

| Эксперимент | Сравниваем | Наблюдаем |
|---|---|---|
| E1: базовый harness | Pi и DeepSeek Harness на одной небольшой задаче | Успех, качество, число шагов, расход, удобство настройки и видимость событий. |
| E2: изоляция | Обычный запуск vs реальное окружение Bubblewrap | Может ли агент читать соседние каталоги; что ломается в инструментировании; удобство запуска. |
| E3: стартовый контекст | `AGENTS.md` vs `AGENTS.md` + обзор vs форк прогретой сессии | Качество, время, токены; учесть цену подготовки обзора/сессии. |
| E4: анализатор памяти | Задачи без накопления новых знаний vs с анализом завершённых сессий | Повторные поиски, бесполезная память, улучшение выполнения последующих задач. |
| E5: ревью | Текущий Antigravity skill и альтернативный вариант | Число циклов, качество находок, ложные замечания, выход за границы задачи. |

Для повторного прогона задачи использовать **одинаковое исходное состояние репозитория до исправления** и одинаковые условия доступа. История предыдущего решения не должна случайно попадать в тестовый вариант; иначе эксперимент загрязнён. Результаты фиксировать вместе с моделью, версией harness и размером контекста.

## 10. Первый этап и последующие возможности

### 10.1. Ядро и данные

- Одна основная БД, на старте SQLite: проекты/рабочие области, профили ролей, задачи, переписка, вопросы и ответы, исполнения, результаты, ссылки на артефакты, выводы анализатора и журнал событий. Это перечень смысловых сущностей, а не утверждённая схема таблиц.
- Бэкенд с API чтения и изменения данных. Клиенты и агенты работают с состоянием через API, а не через прямую запись в файл БД.
- Программный диспетчер: очереди, блокировки рабочих областей, запуск и остановка исполнений, приём результатов, сверка состояния после перезапуска. Правила переходов и очередей не зависят от доступности LLM.
- Реестр задач с очередью «не более одной активной задачи на рабочую область», сохранением истории, вопросов и связей между исполнениями.
- Запуск и остановка временной сессии, продолжение после ответа через старую сессию или новый запуск с handoff.
- Существующее code review с возвратом замечаний разработчику и отдельная задача на production-деплой.
- Базовый учёт расхода и стоимости, если исполнитель предоставляет соответствующие данные.

### 10.2. Первые интерфейсы и роли

- Telegram — основной первый интерфейс человека: беседа с секретарём, постановка и уточнение задач, ответы на вопросы, получение статуса и результатов.
- API — интерфейс для внешних агентов, включая помощника, участвующего в разработке: общение с секретарём, чтение задач и событий, доступные операции над задачами. Telegram использует тот же бэкенд и правила.
- Секретарь, анализатор и разработчик системы входят в первый этап согласно разделу 8.
- API предоставляет данные переписки, задач, вопросов, событий и результатов, чтобы будущий веб-интерфейс использовал существующие операции.
- Схема и поля уточняются на живых задачах. Изменения схемы с первого дня оформляются версионированными миграциями; расширение схемы не требует заранее угадать все будущие поля. Дополнительные изменчивые сведения могут храниться в JSON, основные состояния и связи задаются явно.

### 10.3. Жизненный цикл секретаря и контекст беседы

- Для пользователя беседа продолжается независимо от перезапуска сервиса, смены модели или внутренней сессии. Полная переписка сохраняется в БД; беседа и сессия модели — разные сущности.
- Бэкенд сначала сохраняет входящее сообщение из Telegram или API. Диспетчер запускает обработку и передаёт секретарю новые сообщения, последние реплики, компактную сводку предыдущего разговора и сведения о связанных задачах.
- Секретарь отвечает и выполняет доступные операции через API. Результаты, изменения и ответ сохраняются, ответ доставляется в исходный канал. В ожидании следующего сообщения процесс модели держать запущенным не требуется.
- Сообщения одной беседы обрабатываются последовательно. Уточнения, пришедшие во время исполнения, сохраняются для следующего хода.
- Для следующих сообщений одной беседы секретаря по умолчанию продолжается её сохранённая сессия модели; живой процесс в ожидании человека не требуется. Новые сообщения не означают автоматически новые сессии. Текущая сессия продолжается, пока её контекст укладывается в рабочий бюджет. При приближении к бюджету сохраняется обновлённая сводка и начинается новая сессия. Бюджет настраивается с учётом выбранной модели и реальных разговоров; конкретный порог пока не утверждён.
- Полная история не подставляется в каждый запуск. Секретарь получает ограниченное рабочее окно и может найти и прочитать исходные сообщения при необходимости. Долговечные задачи, решения и договорённости хранятся отдельно со ссылками на переписку.
- Сводка также ограничена рабочим бюджетом: она обновляется, а не бесконечно дополняется. В ней остаются актуальная тема, принятые решения и открытые вопросы; подробности доступны в задачах и архиве. Архив может расти без роста контекста каждого обращения к модели.
- Секретарь пробуждается по сообщению или событию, требующему обсуждения либо объяснения: вопрос исполнителя, результат задачи, ошибка. Простые уведомления бэкенд может доставлять без вызова LLM.
- После сбоя диспетчер восстанавливает обработку сохранённых сообщений, проверяя уже выполненные действия и сохранённые ответы перед повтором. Способ фиксации обработки и защиты от повторного создания задач уточняется в техническом задании.
- Одна беседа может относиться к нескольким задачам или не создавать задач вовсе. Актуальная постановка хранится отдельно от переписки. Секретарь уточняет и готовит задачи; постановка в рабочую очередь требует явного указания человека согласно разделу 3.1.

### 10.4. Рабочая установка отдельно от разработки

- Основная система работает на этом же компьютере, но вне текущего каталога разработки. Согласованный корень рабочей установки — `~/.agent-manager/`:

  ```text
  ~/.agent-manager/
  ├── releases/       # установленные версии приложения
  ├── current         # ссылка на активную версию
  ├── config/         # настройки
  ├── data/           # SQLite и управляемые профили агентов
  ├── sessions/       # сессии, журналы и результаты
  ├── knowledge/      # мастер-хранилище знаний
  │   ├── projects/
  │   └── components/
  └── backups/
  ```

- Обновление переключает версию приложения; БД, профили, сессии и знания сохраняются. Совместимые изменения схемы выполняются миграциями. Исходники разработчика остаются вне корня рабочей установки. Перенос текущих данных из экспериментальных каталогов — отдельная будущая операция с проверкой сохранности истории и ссылок на артефакты.
- Рабочий процесс не импортирует изменяемые исходники из checkout разработчика. Разработка и локальные проверки сами по себе не меняют работающую установку.
- Разработчик использует отдельный checkout и тестовый экземпляр с собственной БД и отдельным Telegram-ботом; рабочие переписка и задачи не используются как тестовые данные по умолчанию.
- Обновление рабочей установки — отдельное явное действие после проверки изменений, включая миграции. Способ установки, переключения версий и восстановления уточняется до первого обновления.
- Приёмочный сценарий: разработчик меняет исходники и перезапускает тестовый экземпляр, а рабочая система продолжает принимать сообщения и хранить задачи. Это не обещание обновления рабочей установки без краткого перезапуска.

### 10.5. Сверка состояния при запуске и явный повтор

- При запуске диспетчер (`TurnProcessor.reconcile_startup_orphans`) сверяет исполнения, оставшиеся в состоянии `running` после завершения или перезапуска процесса. У каждого такого «осиротевшего» хода:
  - статус переводится в `failed`, записывается причина `Turn execution was interrupted by process restart` и время завершения; токен владения (`claim_token`) очищается;
  - если рантайм беседы всё ещё держит активную бронь именно этого хода, бронь (`reservation_token`, `reservation_turn_id`, `reservation_attempt_count`) снимается, а в `blocked_reason` записывается диагностический маркер `Interrupted: <причина>`.
- Переход хода в `failed` и снятие брони выполняются в одной короткой транзакции на ход. Это инвариант восстановления: после сверки не остаётся ни `running`-хода без живого владельца, ни брони без `running`-хода; беседа не остаётся заблокированной без диагностируемой причины.
- Сверка идемпотентна: повторный вызов или чистая база ничего не меняют. Каждый восстановленный ход журналируется на уровне `WARNING` с `turn_id`, `conversation_id` и `attempt_count`; результат запуска журналируется на `INFO`, если сирот нет, и на `WARNING`, если они были закрыты.
- Автоматического повтора модельного вызова нет. Оператор или диспетчер явно вызывает `retry_failed(turn_id)`: ход переходит `failed → pending`, а маркер `Interrupted:` снимается в той же транзакции, чтобы новый запуск мог получить бронь. Блокировка, записанная при неопределённом вызове (не `Interrupted:`), при этом не снимается и остаётся fail-closed.

### 10.6. Фоновый диспетчер очередей (QueueDispatcher)

- Фоновый воркер (`agent_manager.dispatcher.QueueDispatcher` / `BackgroundWorker`) реализует постоянный цикл обработки ходов:
  - Периодически опрашивает базу данных SQLite на наличие ходов со статусом `pending`.
  - Захватывает очередной доступный ход через атомарный SQL-claim (`TurnProcessor.claim_next`).
  - Вызывает инжектированный обработчик (`Handler` или `HandlerFactory`) строго вне транзакций БД.
  - Изоляция сбоев: любое исключение обработчика перехватывается, ход переводится в `failed` с сохранением диагностической ошибки; цикл диспетчера при этом не прерывается и продолжает обработку других ходов.
  - Структурированное логирование: каждое действие воркера сопровождается контекстом `bind_log_context(worker_id=..., turn_id=..., conversation_id=...)` со стабильными маркерами событий (`worker_start`, `turn_claim`, `turn_completed`, `turn_failed`, `worker_stop`).
  - Корректная остановка (`graceful stop`): при получении сигнала остановки воркер завершает текущий активный ход и лишь затем выходит из цикла.

### 10.7. Не нужно для первого этапа

- Веб-интерфейс и визуальная доска: второй этап после уточнения реальной модели данных.
- Автоматически собирать заявки из сторонних каналов; явный ввод через своего Telegram-бота и API входит в первый этап.
- Полностью интеллектуальный оркестратор, который сам переписывает политику работы.
- Автогенерация всех агентов, автоматическая перестройка собственных инструкций.
- Сложная durable execution до каждой модельной операции (пока достаточно надёжной повторной постановки задачи).
- Параллельные исполнители в одной рабочей области и динамические worktree.
- Обязательный отдельный финализатор, исследователь и ревью-агент, если существующих навыков/команд хватает.
- Полноценная панель наблюдения, аналитическая платформа и жёсткие лимиты расходов до получения реальных данных.

## 11. Неопределённости, которые нельзя выдавать за принятые решения

- Структура данных задачи, точные операции API и представления будущего веб-интерфейса. SQLite, Telegram и API для первого этапа уже выбраны; готовая доска не обязательна.
- Нужен ли отдельный исследователь и какова его граница с секретарём. Секретарь и анализатор уже включены в первый этап.
- Какие поля и состояния оркестратор должен изменять сам, а какие — только по подтверждению.
- Продолжать ли зависшую сессию или начинать новую с handoff.
- Точные URI проекта/компонента в OV и порядок публикации проверенных знаний из согласованного мастер-хранилища `~/.agent-manager/knowledge/`. Разделение проектной и компонентной памяти уже требуется (раздел 5.5).
- Права записи анализатора в OV: пока не утверждены; разработчик и секретарь используют поиск/чтение.
- Включение двух-трёх навыков в стартовый контекст или загрузка по требованию; возможная адаптация/объединение brainstorming и grilling для секретаря.
- Полномочия секретаря при редактировании профилей агентов, включая изменение инструментов и доступа к рабочим областям.
- Разогретые сессии vs project overview.
- Финализатор как скрипт / skill / отдельный агент.
- Как устроить интервалы, повторы и критерии остановки ревью.
- Какая конкретная реализация Bubblewrap достаточна и совместима с инструментами.
- Конкретный harness первой версии — должен быть выбран после практического сравнения.
- Точные операции API беседы, привязка сообщений к задачам и способ получения длительных ответов. Жизненный цикл секретаря и ограниченное рабочее окно согласованы в разделе 10.3.
- Бюджет контекста и сводки, способ её обновления и проверка сохранности важных решений при смене сессии.
- Триггеры запуска анализатора и порядок проверки и записи извлечённых знаний.
- Управление процессами, способ переключения релизов, перенос экспериментальных данных в согласованный корень `~/.agent-manager/` и восстановление после неудачного обновления.

## 13. Практический следующий шаг

Сначала уточнить минимальный сквозной контракт: сообщение через Telegram или API → беседа с секретарём → согласованная задача → очередь → исполнение разработчиком → вопрос и продолжение при необходимости → ревью и результат → анализ исполнения. Определить необходимые данные и переходы, не проектируя заранее весь будущий веб-интерфейс.

Затем подготовить техническое задание первого этапа: ядро SQLite/API/диспетчер, три начальные роли и независимая рабочая установка. Эта спецификация фиксирует согласованное направление, но сама по себе не является командой начать реализацию или развернуть рабочую систему.

**Критерий результата первого этапа:** человек через Telegram и внешний агент через API могут общаться с секретарём и работать с общими задачами; разработчик выполняет задачу в ограниченной области, анализатор сохраняет обоснованные выводы; история переживает перезапуск, а разработка не нарушает работу отдельной установки.

Сравнения harness, стартового контекста и памяти из раздела 9 сохраняются как эксперименты. Их результаты уточняют реализацию, но не отменяют согласованный состав первого этапа.
