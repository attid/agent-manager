# Техническое задание: Реализация MCP Endpoint (/mcp) в Agent Manager

**Статус:** Объём MVP согласован; реализация — отдельной задачей
**Область:** `agent-manager/src/agent_manager/api/mcp/`, `agent-manager/src/agent_manager/api/app.py`  
**Назначение:** MVP MCP для личного плагина на сайте ChatGPT: https://developers.openai.com/plugins. Существующее подключение с Bearer уже работает по подтверждению пользователя.

**Границы текущей работы:** Правка только этого плана. Каталог занят другой задачей; код и остальные файлы не менять. Реализация требует отдельной команды пользователя.

---

## 1. Цели и границы проекта

1. **Единая точка входа:** Добавить в существующее FastAPI-приложение Agent Manager эндпоинт `/mcp`.
2. **Zero-Maintenance (автогенерация инструментов):** Автоматически генерировать инструменты MCP из актуальной схемы OpenAPI приложения (`app.openapi()`). Любой новый бизнес-метод FastAPI автоматически становится доступен как MCP-инструмент после перезапуска приложения без написания ручных обёрток.
3. **Текущий доступ:** Сохранить `Authorization: Bearer <token>`. Валидный токен даёт полный доступ. RBAC, scoped-токены и новые уровни прав в MVP не добавляются. Токены не попадают в LLM-контекст.
4. **Без дублирования:** Все существующие API-ручки сохраняются. MCP использует их бизнес-логику; при необходимости допустим точечный вынос общей логики в функции. Массовый рефакторинг не требуется.
5. **Понятность для агента:** Описания помогают выбрать инструмент; ответы сообщают результат, статус, идентификаторы и конкретный способ продолжить или проверить выполнение.
6. **Совместимость с прокси:** Стабильная работа за Traefik, Nginx, Cloudflare Tunnel с поддержкой Server-Sent Events (SSE) и сохранением заголовков.

## 2. Архитектура и сетевой транспорт

### 2.1. Протокол и транспортный уровень
* **Транспорт:** MCP **Streamable HTTP transport** (версия протокола согласуется средствами выбранного SDK), поддерживающий POST (JSON-RPC) и GET (SSE для потоковой доставки событий и сессий).
* **Библиотека реализации:** Официальный Python MCP SDK с ASGI-интеграцией FastAPI/Starlette. Handshake, методы транспорта и управление сессиями делегировать SDK; обеспечить совместный запуск и остановку с приложением.
* **Маршрут:** `POST /mcp` и `GET /mcp` (в зависимости от согласования сессий MCP).
* **Reverse Proxy Friendly:**
  * Сохранение заголовка `Authorization: Bearer <token>`.
  * Корректная работа с SSE: заголовки `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no` (для отключения буферизации в Nginx/Traefik).
  * Корректная обработка `chunked transfer encoding`.

### 2.2. Аутентификация и безопасность
* **Проверка подлинности:**
  * Интеграция с существующим `BearerAuthMiddleware`. Запросы к `/mcp` требуют валидный Bearer-токен.
  * Проверка токена выполняется **на каждом HTTP-запросе**, включая запросы установленной MCP-сессии.
  * При отсутствии или невалидности токена возвращается HTTP `401 Unauthorized`.
* **Защита от утечки токенов:**
  * Никакие токены, ключи и заголовки авторизации не передаются в параметры инструментов, схему `inputSchema`, возвращаемые результаты или описания.
  * Внутренний ASGI-вызов API получает серверный заголовок Authorization без участия модели. Токен не передаётся через query-параметры URL и не журналируется.
* **Маскирование ошибок:**
  * Стек вызовов (stack traces), внутренние пути файловой системы и параметры подключения к БД маскируются. Клиент получает понятную ошибку выполнения инструмента с кодом состояния HTTP и кратким описанием причины.
* **Граница MVP:** Сохраняется существующая проверка токена на доступ. Новую систему прав не реализовывать.

## 3. Автоматическая генерация инструментов из OpenAPI

### 3.1. Фильтрация и формирование реестра
При запуске приложения после регистрации API-маршрутов генератор анализирует `fastapi_app.openapi()`. Реестр обновляется после рестарта: каждый боевой деплой сопровождается рестартом. Обновление на лету не требуется. Новая ручка не требует отдельной MCP-регистрации.

* **Исключаемые маршруты:**
  * Служебные и технические: `/health`, `/metrics`.
  * Документация: `/docs`, `/redoc`, `/openapi.json`.
  * Сам MCP-эндпоинт: `/mcp`.
* **Именование инструментов:**
  * Стабильный уникальный идентификатор инструмента строится на базе `operationId` (например, `create_task_tasks_post` -> `tasks_create` или прямое использование нормализованного `operationId`).
  * Правило нормализации должно исключать спецсимволы и соответствовать регулярному выражению MCP имени инструмента (`^[a-zA-Z0-9_-]{1,64}$`).

### 3.2. Преобразование схем параметров (`inputSchema`)
* **Объединение источников:** Использовать отдельные объекты `path`, `query`, `body` для применимых источников, чтобы одинаковые имена не конфликтовали.
  * Path-параметры (например, `{task_id}`).
  * Query-параметры (фильтрация, пагинация: `limit`, `offset`, `status`).
  * Request Body (JSON-схема тела запроса).
* **Разрешение ссылок ($ref):**
  * Перенос `$ref` из OpenAPI в самодостаточную схему инструмента. Рекурсивные типы сохраняют ссылки внутри итоговой схемы без бесконечного разворачивания.
* **Точность типов и валидации:** Не добавлять новых ограничений поверх существующего API.
  * Сохранение обязательных полей (`required`).
  * Сохранение типов (`string`, `integer`, `boolean`, `array`, `object`), форматов (`date-time`, `uuid`) и ограничений (`enum`, `minimum`, `maximum`, `maxLength`).
  * Корректная обработка `nullable` (типы `["string", "null"]` или `anyOf`).
  * Сохранение семантики: отсутствие ключа в словаре отличается от явной передачи `null`.

### 3.3. Аннотации MCP (Tool Annotations)
Для каждого инструмента выставляются стандартные подсказки MCP:
* `readOnlyHint`:
  * `true` для идемпотентных запросов чтения (`GET`).
  * `false` для создания, модификации, архивации или запуска операций.
* `destructiveHint`:
  * `true` для деструктивных операций: удаление, отмена задачи (`/cancel`), остановка процессов, архивация.
* `idempotentHint`:
  * `true` для `GET`, `PUT` с гарантией идемпотентности.
* **Метаданные без дублирования:** Аннотации определяются реальным поведением API, а не только HTTP-методом. Разрешены уточнения непосредственно у маршрута; отдельные ручные MCP-обёртки бизнес-функций не нужны.
* **Текстовое описание:**
  * Объясняет, когда вызывать инструмент и чем он отличается от похожих. Включает `summary`, детальный `description` из OpenAPI, а также явное предупреждение о существенных побочных эффектах (side effects: запуск фонового воркера, отправка в очередь, изменение состояния репозитория).

## 4. Диспетчеризация и выполнение вызовов

### 4.1. Механизм выполнения
* Вызовы инструментов маппятся на внутреннее выполнение методов FastAPI через внутренний ASGI-клиент (`httpx.AsyncClient(transport=ASGITransport(app=app))`) с сохранением middleware, зависимостей и валидации FastAPI. Прямой обход обработчиков и копирование бизнес-логики в MCP не требуются. Клиент закрывается вместе с приложением; lifespan приложения не запускается повторно на каждый вызов.
* Передаются исходные заголовки авторизации и контекст безопасности.
* Не создаётся сетевой оверхед (вызовы происходят in-process внутри того же процесса Python).

### 4.2. Идемпотентность и безопасность транзакций
* **Без слепых повторов:** Инструменты с `destructiveHint=true` или `readOnlyHint=false` не должны автоматически повторяться MCP-сервером в случае сетевого сбоя клиента.
* **Поддержка ревизий и конфликтов:** При конфликте версий (HTTP 409 Conflict) или ошибке валидации (HTTP 422 Unprocessable Entity) возвращается структурированная ошибка с деталями ответа API.
* **Долгие операции:** Использовать существующие фоновые задачи/запуски Agent Manager. Возвращать подтверждённый ID, известный статус и конкретный инструмент проверки с аргументами; не удерживать вызов до завершения фоновой работы. Отдельную систему очередей в MVP не добавлять.
* **Тайм-ауты:** Ожидание настраивается с учётом ChatGPT и используемого прокси. 60 секунд — не обязательный стандарт OpenAI. Истечение ожидания не означает отмену или провал операции. Если итог неизвестен, явно сообщить это, вернуть известный ID и способ проверки. При отсутствии ID указать доступный поиск через существующий API, не придумывая результат. Изменяющий вызов автоматически не повторять.
* **Обязательный сценарий `/ask`:** По наблюдению пользователя диалог создаётся, но секретарь не успевает ответить, и агент ошибочно сообщает о сбое. Различать создание диалога и готовность ответа. При подтверждённом создании возвращать ID диалога, состояние ожидания ответа и реальный инструмент/аргументы для чтения ответа. Не выдавать отсутствие готового ответа секретаря за неуспешное создание диалога. Если создание не подтверждено, сообщать неопределённость и способ проверки. Повторно создавать диалог автоматически нельзя.

### 4.3. Формат ответа
* Ответ инструмента упаковывается в стандартный `CallToolResult`:
  * Понятный текст (`TextContent`) и структурированные данные; при объявленном `outputSchema` соблюдать его. Сохранять полезные данные API.
  * Для операций с продолжением сообщать, что выполнено, текущий статус, ID и точный следующий инструмент с аргументами. Не выдумывать статусы или инструменты.
  * Ошибка должна объяснять причину и доступный способ исправить запрос или проверить состояние. Не раскрывать секреты и внутреннюю диагностику.
  * При ошибке API: поле `isError=True` с сохранением кода состояния (HTTP Status Code) и структурированного тела ошибки.

## 5. Основной клиент и границы MVP

- Основной и обязательный клиент — личный плагин на сайте ChatGPT. Сохраняется уже работающий у пользователя Bearer-доступ.
- Ориентир по транспорту и метаданным — [официальная документация OpenAI Plugins](https://developers.openai.com/plugins/build/mcp-server): стабильный HTTPS `/mcp`, Streamable HTTP, корректные схемы, аннотации, результаты и ошибки.
- OAuth, публичная публикация, Custom Actions и отдельные инструкции для Claude/Cursor в MVP не входят. Требования портала публичной публикации не переносить на личное подключение.
- После изменения инструментов проверить перечитывание метаданных ChatGPT; при необходимости обновить соединение или начать новый чат. Рестарт сервера обновляет серверный реестр, но сам по себе не гарантирует сброс клиентского кэша.

## 6. Программа испытаний и приёмочные тесты

Для приёмки реализации создаётся тестовый набор (включая автоматизированные тесты в `agent-manager/tests/test_mcp.py`):

1. **Инициализация и список инструментов:**
   * Handshake `initialize` с MCP клиентом.
   * Проверка вызова `tools/list`: возвращается полный список сгенерированных инструментов, совпадающий по составу с бизнес-эндпоинтами OpenAPI.
2. **Аутентификация:**
   * Запрос к `/mcp` без токена -> отказ (401).
   * Запрос с невалидным токеном -> отказ (401).
   * Запрос с текущим валидным токеном -> успешный handshake и доступ ко всем операциям.
3. **Чтение данных:**
   * Вызов инструмента чтения списка задач (`tasks_list`) -> возвращается структурированный JSON со списком задач.
   * Вызов инструмента получения конкретной задачи по `task_id`.
4. **Модификация и транзакции:**
   * Создание тестовой задачи через MCP-инструмент -> задача создаётся в БД, возвращаются реквизиты.
   * Обновление задачи.
5. **Обработка ошибок и валидации:**
   * Передача невалидных параметров -> возврат `isError=True`, HTTP 422 с перечислением невалидных полей.
   * Запрос несуществующей задачи -> HTTP 404 в результате вызова.
   * Поддерживаемый существующим API конфликт ревизий -> HTTP 409 с описанием конфликта.
   * Долгая операция и тайм-аут: корректный статус/неопределённость, отсутствие автоматического повторного изменения, существующий инструмент проверки с корректными аргументами.
   * `/ask`: диалог создан, ответ секретаря задержан — агент получает ID и состояние ожидания, проверяет ответ в том же диалоге; ошибочное сообщение о провале и повторное создание отсутствуют.
6. **Корректность типов и null:**
   * Проверка передачи вложенных JSON-структур.
   * Проверка явного `null` против отсутствующего поля (omitted).
   * Проверка совпадающих имён path/query/body, вложенных и рекурсивных схем, уникальности имён инструментов.
7. **Автогенерация после рестарта:**
   * Тест добавления нового роута в тестовый экземпляр FastAPI -> после старта нового экземпляра приложения новый инструмент появляется в `tools/list` без ручной регистрации. Обновление работающего экземпляра не требуется.
8. **Работа за Reverse Proxy:**
   * Проверка через используемый reverse proxy и внешний HTTPS URL с сохранением авторизации и потоковой передачи.
9. **Проверка в ChatGPT:**
   * На изолированных тестовых данных проверить существующее личное Bearer-подключение, чтение, создание/обновление, выбор нужного инструмента и продолжение по возвращённому ID, включая `/ask`.
   * Изменяющие проверки проводить только на выделенных тестовых сущностях; не запускать реальные задачи пользователя для приёмки.

## 7. Артефакты поставки

1. Модуль генератора и ASGI-роутера: `agent_manager.api.mcp`.
2. Интеграция точки монтирования в `agent_manager.api.app:create_app`.
3. Автоматические тесты: `tests/test_mcp.py`.
4. Краткая инструкция по личному подключению на сайте ChatGPT: HTTPS `/mcp`, текущий Bearer, обновление метаданных после деплоя, проверка чтения/записи и состояния долгой операции.

**Критерий MVP:** ChatGPT обнаруживает инструменты, читает и меняет тестовые данные через существующий API, получает понятные ошибки и понимает, как дождаться результата долгой операции. Все существующие ручки сохраняются; бизнес-логика не дублируется.
