# ТЗ: Pi Runner + Bubblewrap — MVP 0.1

**Цель:** запускать одну задачу разработки через Pi в отдельной локальной песочнице, сохранять результат и сессию. Это **исполнитель**, не оркестратор.

## 1. Границы первой версии

- Ubuntu/Linux, установленный Pi и `bubblewrap` (`bwrap`).
- Один проект за запуск; одна активная сессия в рамках экземпляра Runner.
- Запуск вручную из CLI: выбрать конфигурацию проекта, передать текст задачи, получить результат и пути к артефактам.
- Никаких Trello, Telegram, диспетчера, субагентов, автоматического ревью, деплоя или записи в OpenViking на этом этапе.
- Проектные `AGENTS.md` остаются в репозитории; локальные настройки Runner и приватные инструкции — снаружи репозитория.

## 2. Конфигурация проекта

Для каждой рабочей роли отдельный конфиг, например `skynet-developer`:

- ID роли; корневой путь к исходникам; рабочий каталог внутри песочницы.
- Отдельный HOME и каталог для файлов сессий/результатов; по умолчанию вне репозитория.
- Список **явно разрешённых** дополнительных каталогов (по умолчанию пустой).
- Модель/провайдер и разрешённый набор инструментов Pi; возможность сменить модель без смены роли.
- Пути к локальным инструкциям/контексту; не наследовать скрытно пользовательские глобальные расширения, skills и другие проекты.
- Настройки доступа к сети; по умолчанию сеть доступна для LLM/API и разрешённых инструментов.

Не копировать реальные секреты в проектный HOME или журналы; способ выдачи необходимых учётных данных берётся из существующей схемы и не разрабатывается в данном MVP.

## 3. Запуск и выполнение

1. Runner читает конфиг, проверяет пути и запускает **сам процесс Pi внутри `bwrap`** (не только отдельные команды `bash`).
2. Pi получает нужные инструкции (`AGENTS.md` + локальные файлы) и конкретную задачу.
3. Репозиторий доступен на запись для редактирования исходников; всё остальное открывается минимально необходимым способом: системные библиотеки и исполняемые файлы — только чтение, временные и служебные каталоги — отдельно.
4. Сессия пишется в постоянный каталог; при завершении Runner сохраняет её ID/путь, итоговый ответ, статус и код завершения, модель (если доступна), время и сведения о расходе токенов (если доступны).
5. При ошибке, остановке или перезагрузке исходники и история сессии сохраняются. Должна быть команда возобновления по ID сессии; точное восстановление незавершённого tool call не требуется.
6. Должна быть возможность принудительно остановить процесс, не оставляя фоновых дочерних процессов.

**Важно:** изменение исходников разрешено; автоматический `git commit`, `push`, деплой и обращения к production не входят в рабочий цикл. Для их запрета не полагаться только на системный промпт: предусмотреть техническую политику инструментов/команд и отдельно проверить её границы. Для read-only анализа Git доступ к истории допустим.

## 4. Требования к изоляции

- Процесс агента не видит исходники, HOME и данные соседних проектов.
- Не монтировать целиком реальный `$HOME`, `.ssh`, конфиги Git с учётными данными, Docker socket, системные секреты.
- Снаружи проекта разрешаются только явно перечисленные read-only зависимости и отдельные необходимые пути.
- При отсутствии `bwrap` либо невозможности создать песочницу — **отказ от запуска**, а не запуск без изоляции.
- Проверка изоляции проводится изнутри Pi, в том числе через `bash`, Python и попытку обращения к абсолютному пути соседнего проекта.
- Учесть, что доступный интернет не изолирует внешние API, а запрет Git-команд внутри writable-репозитория сложнее, чем простая фильтрация строки: конкретную модель ограничений и её обходы задокументировать, не обещая абсолютной защиты.

## 5. CLI и артефакты

Минимальный интерфейс (названия команд примерные, не привязка к конкретному API):

```text
runner run --agent skynet-developer --task task.md
runner resume --session <id>
runner stop --session <id>
runner inspect --session <id>
```

Формат результата — JSON с `session_id`, `agent_id`, `status`, `started_at`, `ended_at`, `session_path`, `summary_path`, `exit_code`, `usage` (если есть), `changed_files`. Вывод событий и ошибок — в отдельный журнал. Задача и её результат доступны без чтения полного транскрипта.

## 6. Приёмочные проверки

1. Агент прочитал `AGENTS.md`, выполнил небольшое изменение в тестовом репозитории; diff остался в рабочем дереве, сессия сохранилась.
2. Попытки прочитать файл соседнего проекта и настоящий HOME неуспешны; системные утилиты и тесты проекта при этом работают.
3. Можно остановить Runner и возобновить сессию после перезапуска.
4. Параметры модели можно поменять без переноса репозитория или файлов проектной памяти.
5. Запуск без работающей изоляции запрещён.
6. Проверены границы запретов commit/push и отсутствие доступа к production; выявленные обходы честно зафиксированы.
7. Есть короткая инструкция установки, пример конфига и запуск на тестовом проекте без реальных секретов.

## 7. Вне MVP и открытые решения

- **Потом:** доска задач, очереди, DevOps-агенты, ревью-конвейер, Telegram, OpenViking, анализатор памяти, сравнение harness.
- **Определить при реализации:** использовать Pi RPC-процесс или SDK в отдельном дочернем процессе; главное — весь исполнитель должен быть внутри песочницы, а жизненный цикл контролируется Runner.
- **Не принимать без тестирования:** что Bubblewrap сам запрещает Git push, доступ к разрешённым сетевым сервисам или запуск дочерних команд; для этого требуются дополнительные ограничения либо иной набор инструментов.

**Критерий готовности:** одна реальная безопасная задача решается Pi в изолированном проекте; её ход, результат и история доступны после перезапуска; отсутствие доступа к чужим каталогам проверено экспериментально.
