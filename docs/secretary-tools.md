# Инструменты Секретаря (Platform Controller & Secretary Tools)

Секретарь (`system-secretary`) в Agent Manager выполняет роль главного диспетчера и контроллера всей агентной платформы. Работая через Telegram, он имеет доступ к набору инструментов (доступных через policy `pi-runner` и REST API Agent Manager).

---

## 1. Задачи и сессии разработки

### `resolve_workspace(workspace, agent_id)`

Проверка без изменения данных через `GET /workspaces/resolve`. Возвращает
`host_path`, `sandbox_path`, `agent_id`, `profile_revision`, `project_read_only`
и `network`. Каталог проекта всегда монтируется как `/workspace`; если на хосте
выбран `/home/user/Projects`, внутри это `/workspace`, а не `/workspace/Projects`.
Несуществующий явно указанный путь не подменяется каталогом по умолчанию.
Реальный HOME и его родители запрещены файловой границей Runner.

Если workspace не указан, используется `runner_config.project` выбранного агента,
затем каталог worker по умолчанию. Произвольные имена не регистрируются автоматически.

### `list_tasks(status, workspace)`
- **Назначение**: Просмотр задач в очереди с фильтрацией.
- **Параметры**:
  - `status` (string, опц.): `incoming`, `in_progress`, `ready_to_commit`, `done`, `failed`.
  - `workspace` (string, опц.): имя воркспейса проекта (например `agent-manager`).

### `get_task(task_id)`
- **Назначение**: Получение полной карточки задачи, статуса, метаданных и отчёта.

### `create_task(title, description, workspace, agent_id, status, task_type)`
- **Назначение**: Постановка задачи выбранному исполнителю.
- **Параметры**:
  - `title` (string): заголовок задачи.
  - `description` (string, опц.): подробное ТЗ.
  - `workspace` (string, опц.): существующий путь на хосте или явно настроенный alias.
  - `agent_id` (string, опц.): исполнитель; при отсутствии используется агент worker по умолчанию.
  - `status` (string, по умолчанию `incoming`): статус.
  - `task_type` (string, по умолчанию `coding`): `coding`, `devops`, `research`.

### `update_task(task_id, status, title, description, workspace, agent_id)`
- **Назначение**: Редактирование ТЗ, исполнителя, каталога или статуса. Перед запуском и изменением маршрутизации инструмент проверяет эффективного агента и workspace.

`incoming` сохраняет задачу и не запускает её. Явная команда выполнить задачу
передаётся как `in_progress`; тип `research` не меняет исполнителя. Инструменты
создания и запуска возвращают фактический контекст исполнения. Worker повторно
проверяет каталог перед запуском и сохраняет контекст в `metadata.execution_context`.
Назначение хранится в отдельном поле `tasks.agent_id` (миграция `0006_task_agent`);
старые задачи с NULL используют прежнего агента worker по умолчанию.

### `get_task_logs(task_id)`
- **Назначение**: Структурированный просмотр исполнительного отчёта задачи. Возвращает `{status: "ok"|"failed", task_id, title, task_status, updated_at, summary, error, changed_files, review}`; при ошибке — `{status: "failed", http_status, error}`.

### `resume_task_session(task_id, message)`
- **Назначение**: Отправка дополнительных инструкций агенту-разработчику и продолжение его существующей сессии.

## 2. Управление Агентами (Agent Profiles)

### `list_agents()`
- **Назначение**: Просмотр списка всех зарегистрированных агентов в платформе.

### `get_agent(agent_id)`
- **Назначение**: Получение текущей конфигурации, инструментов, скилов и системного промпта агента.

### `create_agent(agent_id, name, role, tools, skills, system_prompt, runner_config)`
- **Назначение**: Регистрация нового агента проекта.
- ID и роль свободные; `<project>-developer` — пример, а не обязательный формат. Префикс `system-*` обозначает платформенных агентов.
- Сначала секретарь отправляет полный Markdown-черновик и ждёт одобрения. После одобрения инструмент синхронно вызывает `POST /agents`, возвращает `applied` с профилем и ревизией. Существующий ID даёт `409`, без upsert.
- `runner_config` задаёт конфигурацию Runner, включая `project` (путь хоста), `project_read_only`, `network`. Если поля не указаны, действуют стандартные настройки Runner.

### `update_agent(agent_id, system_prompt, tools, skills, name, role, runner_config)`
- **Назначение**: Синхронный `PATCH /agents/{id}` с `expected_revision`; меняет только переданные поля. Поля `runner_config` объединяются с текущей конфигурацией. Ответ содержит сохранённый профиль и ревизию. `405` не является задержкой синхронизации; ошибка не обходится повторным созданием агента.

## 3. Управление Скилами (Skills)

### `list_skills()`
- **Назначение**: Список всех установленных скилов в `~/.local/share/agent-manager/skills` с описанием из `SKILL.md`.

### `install_skill(name, source)`
- **Назначение**: Установка скила из директории (например из каталога OpenViking или локальной папки).

### `create_skill(name, skill_md, scripts)`
- **Назначение**: Создание нового скила «на лету» с генерацией `SKILL.md` и вспомогательных скриптов.

---

## 4. База Знаний (Knowledge Base)

### `list_knowledge(category)`
- **Назначение**: Просмотр дерева базы знаний (`projects`, `components`, `docs`).

### `read_knowledge(query)`
- **Назначение**: Полнотекстовый поиск и чтение файлов документации, правил компонентов или саммари проектов.

### `write_knowledge(category, name, content)`
- **Назначение**: Сохранение произвольного документа в базу знаний с автоматическим git-коммитом в репозиторий знаний.

### `save_project_summary(name, summary)`
- **Назначение**: Обновление карточки проекта (`knowledge/projects/<name>/summary.md`).

### `update_component_rules(component, rules)`
- **Назначение**: Обновление архитектурных правил компонента (`knowledge/components/<component>/rules.md`).

### `attach_document(target)`
- **Назначение**: Отправка документа или файла логов напрямую пользователю в Telegram.
- **Область действия**: Запрос привязан к одному вызову инструмента и одному ходу. Runner передаёт идентификатор хода в `/session/turn.json`, policy сохраняет его вместе с `toolCallId`, а обработчик добавляет `[SEND_FILE: <target>]` только для текущего хода и подтверждает запись после сохранения ответа. Продолжение беседы на постороннем ходу не повторяет старую отправку; новый осознанный запрос того же файла отправляет его снова. Legacy-записи без идентификатора хода остаются историей и не воспроизводятся.

## 5. Долгосрочная память OpenViking

### `openviking_search(query, limit)`
- **Назначение**: Семантический поиск по долговременной памяти, внешним документам и коду через локальный сервис OpenViking (`http://127.0.0.1:1933`).

### `openviking_read(uri)`
- **Назначение**: Чтение полного текста ресурса по URI вида `viking://...`.

---

## 6. Триггеры и Git Engine

### `trigger_review(task_id, instructions)`
- **Назначение**: Принудительный перезапуск раунда Code Review независимым ревьюером (`system-code-reviewer`).

### `trigger_commit_push(task_id, push, message)`
- **Назначение**: Безопасный коммит измененных файлов через `GitEngine` с проверкой GitHub Actions CI (`gh run watch`).

### `trigger_rollback(task_id)`
- **Назначение**: Безопасный откат незакоммиченных изменений (`git restore --staged --worktree`) и удаление созданных файлов.

### `trigger_analysis(task_id)`
- **Назначение**: Запуск агента `system-log-analyzer` для анализа сессии завершенной задачи и формулирования предложений в Базу Знаний.

## Подтверждения, ошибки и совместимость с существующими сессиями

Обязательные инструкции платформы добавляются при каждом запуске секретаря,
включая продолжение существующей сессии. Пользовательский системный промпт и
закреплённая версия профиля не переписываются. `resolve_workspace` подключается
к исполнению секретаря, если у его закреплённого профиля есть `create_task`.

Изменение профиля допускается после одобрения показанного Markdown. Это правило
диалога в промпте; сервер не удостоверяет согласие пользователя отдельным токеном.
Сохранённый Markdown включает filesystem/network policy и skills для проверки.

Ошибки инструментов возвращаются с `isError` и `status=failed`. Потеря ответа
на запись или HTTP 5xx имеют неизвестный исход: сначала нужно прочитать состояние,
а не повторять запись. `write_knowledge` и `attach_document` остаются отложенными
до завершения хода: для отправки черновика вызываются оба инструмента и завершается
ответ. Профили изменяются через API; черновики хранятся в `docs/drafts`.

Исторические `created_agents.json` и `written_knowledge.json` сохраняются как аудит.
Рядом появляются `*.applied.json` с подтверждёнными записями. Продолжение беседы не
применяет их повторно. Старый запрос создания никогда не заменяет существующий
профиль. Записи agents/ из старой очереди документов больше не переопределяют API.

`project_read_only=true` задаёт настоящий read-only mount; текстового запрета
в промпте при наличии bash недостаточно. `network=false` отключает сеть всей
песочницы, включая API модели. Для модели с доступом к провайдеру и инструментов
без внешней сети нужен отдельный транспорт; здесь он не реализован. Тесты policy
проверяют маршрутизацию и настройки без обращения к LLM.
