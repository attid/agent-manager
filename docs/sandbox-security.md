# Модель ограничений MVP

## Проверяемые границы

* Новый mount namespace начинается с пустой файловой системы; реальный HOME,
  соседние проекты, `/run`, Docker socket и глобальные Git credentials не монтируются.
* `/usr`, библиотеки, публичные сертификаты/настройки DNS и явно заданные зависимости
  открываются read-only. Это доверенная локальная система; секреты, заранее сохранённые
  в `/usr` или разрешённой зависимости, не обнаруживаются автоматически.
* Исходники, отдельный HOME роли и транскрипт текущей сессии writable. `/tmp` и
  `/dev` отдельные. Окружение очищено; credentials передаются только по явным именам.
* `.git` корневого checkout монтируется read-only. Обычный commit и прямая запись
  через Python в эти метаданные неуспешны. `git log` разрешён.
* Pi загружает обработчик `tool_call`, запрещающий распространённые прямые формы
  `git commit` и `git push`, включая абсолютный путь к Git и обычные опции `-C`, `-c`.
* Если bwrap отсутствует или создание sandbox не удалось, код агента не запускается
  на хосте. Никакого fallback на несандбоксированное выполнение нет.
* PID namespace, `--die-with-parent`, отдельная process group и принудительное
  завершение уничтожают дочерние процессы, включая `setsid`-потомков. Проверены
  штатный stop и SIGKILL самого Runner; перезагрузка ОС отдельно не моделировалась.

## Известные обходы и пределы

Обработчик Bash — защита от случайного действия, не shell parser и не security boundary.
Он не распознаёт, например, `g=git; "$g" push`, вызов из Python, Git aliases,
динамическую сборку строки или отдельный скрипт. Фикстура `tests/test_policy.mjs`
проверяет такие границы распознавания без обращения к удалённым репозиториям.
При обходе обработчика read-only mount всё равно защищает `.git` исходного checkout.
Агент может создать другой Git-каталог в writable-области и сделать commit там;
полного запрета алгоритма создания Git-объектов нет. Вложенные репозитории не получают
отдельной защиты `.git` и должны быть исключены из тестового проекта.

`network=true` сохраняет сеть хоста. Сервис без авторизации, переданный API-ключ,
credentials внутри исходников/`.git/config`, metadata endpoint или локальный TCP
сервис могут быть доступны агенту. Отсутствие credentials в HOME не доказывает
отсутствие доступа к production. Push может изменить remote даже если последующая
запись локального tracking ref не удалась. HTTP/Git/SDK через Python обходит
командный обработчик. Deploy также не имеет универсального запрета на уровне сети.
Настоящего production в тестах не касаемся.

`network=false` создаёт network namespace без сети; если это запрещено ОС, запуск
отклоняется. Прямое обращение Pi к внешней LLM тогда тоже невозможно. Для доступной
LLM при запрещённых прочих API потребуется отдельный шлюз/egress-механизм, который
не входит в эту реализацию. Сохранение сетевого namespace также не является
защитой от доступных host abstract Unix sockets.

Разрешённые runtime/dependency-пути и `pi_command` — доверенная административная
конфигурация. Не включайте туда каталоги с секретами, чужими исходниками и сокетами.
История Pi и HOME writable агентом; это не защищённый аудит. Runner не переписывает
историю и не обещает скрывать переданные credentials от инструментов того же Pi.
Защиты от эксплуатации ядра, исчерпания памяти/диска и всех побочных каналов нет.

## Статус приёмки

Автотестами проверяются реальные mount-ограничения, Bash/Python-доступ к соседнему
пути, настоящий Pi с детерминированным провайдером, запрет прямого push обработчиком,
read-only Git, сохранение и resume, stop, SIGKILL Runner, блокировка конкурирующего
запуска и fail-closed при отсутствии/неисправности bwrap.

Задача, самостоятельно решённая реальной LLM, отсутствие production-доступа при
общей сети и восстановление после загрузки ОС не доказаны этими проверками.
Итоговый критерий готовности исходного ТЗ полностью не закрыт: это исполняемый
прототип для локальных испытаний с указанной моделью ограничений.
